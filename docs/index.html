MCP server · D2L Brightspace

Build a course without opening the LMS

An MCP server for Lamakū, the University of Hawaiʻi's Brightspace instance. It reads your courses like the others do. It also writes to them: authored pages, uploaded video, discussions, assignments, and whole course packages.

Get started Source

What it is for

And when something simpler will do.

The other D2L MCP servers are read-only. They check grades and due dates, which is a real job and a different one. If you want to ask what is due on Thursday, use one of those.

This one exists to construct a course and put it in Brightspace: modules, pages with real media in them, forums with the discussion prompts already written, an assignment with a rubric to come, quizzes carrying their answer keys.

Writes land in a live course, so most of the design here is about not doing that carelessly.

54 tools

Reading, authoring, and the student side. Every write route verified against a real sandbox by creating an object and deleting it again.

Preview before write

The first call returns a plan and a token. Nothing reaches Brightspace until you call again with it.

FERPA by default

Student names never reach the model unless you deliberately ask. Handles are stable so an assistant can still reason about them.

Install

Node 20 or newer. A UH account with Duo.

# clone, install, build
git clone https://github.com/JesseTho/lamaku-mcp
cd lamaku-mcp
pnpm install
pnpm build

# opens a browser: sign in and approve Duo yourself
node dist/cli.js login

The session is stored encrypted under your user profile. It lasts about a day of idleness and expires hard after a few days, at which point you run login again.

Register with Claude Code

claude mcp add lamaku -- node /absolute/path/to/lamaku-mcp/dist/index.js

Another institution

Set BRIGHTSPACE_HOST to your own D2L hostname. The API layer is not UH-specific, but only Lamakū has been tested, and the login flow assumes an interactive browser. For anything headless or shared, see OAuth in the README.

How writes are gated

Two gates, both load-bearing.

A role preflight runs first and refuses before spending the call if your role in that course cannot do the thing. The same person holds different roles in different courses, and the API enforces them inconsistently, so this turns a bare 403 into a straight explanation.

Then the confirmation token. Calling a write tool returns only a preview of what would be sent. Nothing reaches Brightspace until you call the same tool again with the token that preview carried.

// first call: nothing has happened yet
{
  "status": "confirmation_required",
  "action": "delete_discussion_forum",
  "willDo": {
    "course": "Sandbox 2",
    "name": "Module 3: diagnosing failed feeds",
    "topicCount": 1,
    "warning": "Deletes the forum, its 1 topic(s), and every post inside them."
  },
  "confirmToken": "0vVbBxC1c2gq",
  "expiresAt": "2026-08-24T20:03:50Z"
}

Tokens are single use, expire in five minutes, and are scoped to the action they were minted for. A token approved for one preview cannot authorise a different operation.

Everything starts hidden

New objects are created hidden from students on purpose, so a half-built course is never briefly live. release_course_content is the deliberate last step, and it previews exactly what becomes visible before it does anything.

Build a course, end to end

Order matters, mostly because media paths do not exist until the media does.

  1. Create the modules

    One create_content_module per module. They arrive hidden and in creation order; update_content_module takes a sortOrder if you need to rearrange.

  2. Upload the media first

    create_content_file takes video, audio, images, PDFs and caption files. Each call returns the enforced content path and an embedAs snippet with that path already filled in.

    Doing this after the pages means rewriting every page once you learn the paths.

  3. Write the pages

    create_content_page takes body HTML and wraps it in a template. Paste the embedAs snippets where the media belongs.

  4. Add the parts a cartridge cannot carry

    create_content_link for external sources, then create_discussion_forum, create_discussion_topic and create_assignment. No package format expresses these, so they have to be authored.

  5. Give each module a cover

    set_module_description with an imagePath from step 2. Brightspace renders an image in a module description as that module's cover image.

  6. Import what the API cannot author

    Quiz questions are the clearest case: Brightspace exposes GET for them and no create route, so create_quiz can only make an empty shell. A Common Cartridge carries QTI, and import_course_package creates the questions, their answer keys and their feedback from it.

    Poll get_import_status until it reports COMPLETED.

  7. Release it

    release_course_content walks the whole tree and unhides in one pass, after showing you the list.

What an import can carry

A Common Cartridge brings pages, weblinks, files, QTI quizzes and question banks, discussion topics and LTI links. A Brightspace .zip brings all of that plus D2L-native objects: rubrics, release conditions, grade schemes.

That second one is the practical way to move a rubric between courses while the rubric API waits on le 1.97. Groups, sections, attendance and awards cannot be expressed in either format.

Import adds, it does not replace

Importing the same package twice produces two copies of everything. Import into an empty course, or check for overlap first.

The FERPA guard

Why student names do not reach the model.

Student names, usernames, emails and institutional IDs are protected education records. This server hands course data to a language model, and from there into a vendor's logs, so by default it does not emit them.

Students become a stable handle like student:4f2a91, an HMAC under a salt generated on your machine and never transmitted. Not reversible, not comparable across installs, and stable across calls, so an assistant can still reason about the same student who missed lab 3 without knowing who that is.

The raw userId is dropped as well. It is a direct key back into Brightspace and into anything sharing the same institutional ID, so pseudonymising only the name would not be enough.

Course staff are not redacted. A co-instructor's name is not a protected record, and hiding it makes a roster unreadable for no gain. Pass revealStudents: true when you have deliberately asked for real names.

A disclosure control, not an access control

You can read your roster in Brightspace whenever you like. The point is keeping it out of prompts and model retention unless you meant to put it there. SECURITY.md covers what it does and does not protect.

What it cannot do

Four different kinds of no, which a column of red crosses would flatten into one.

CapabilityWhy
Quiz questions, directly no route Brightspace exposes GET and no create route. Import a cartridge; that works and is verified.
Rubric authoring version Needs le 1.97+; Lamakū serves 1.96, one version short. A Brightspace .zip import carries rubrics today.
Grade value writing untested The sandbox has no student enrolments, and trying it in a live section would alter a real record.
Grade item listing no route get_grades returns the caller's own grades. Items can be created and deleted by id but never enumerated.
Course creation admin Org-level permission, not available to an instructor account.
Groups, sections, attendance, awards absent Not implemented, and not expressible in a course package either.
OAuth on another instance unproven Scaffolded against auth.brightspace.com, never exercised outside UH. Treat as untested.

Reading a 404 against a 400

Brightspace separates these usefully when you are probing. A 404 means the route does not exist at that API version. A 400 means it exists and rejected your input. That is how the rubric split above was settled.

One caveat on the same theme: a 400 does not prove you have permission. Several routes validate the body before checking the role, so probing with a malformed payload over-reports your access. Only a real create proves anything.
